# LedgerLine Threat Register

Threat register for the Snovasys Fresher Hiring Challenge 2026. PostgreSQL 18.6 V1–V10 migration validation, the V10 transaction constraint, journal trigger/function state, and Hibernate schema validation were verified during the 2026-11-10 recovery. Functional integration and concurrency tests use H2; PostgreSQL financial-operation behavior remains unverified.

| Threat | Attack scenario | Potential impact | Planned mitigation | Required verification test | Implementation status |
|---|---|---|---|---|---|
| Authentication compromise | An attacker guesses passwords, reuses leaked credentials, or exploits weak password storage to sign in as a customer. | Account takeover, exposure of financial history, and unauthorized money movement. | Store only a modern one-way password hash; enforce password policy; use generic login failures; add rate limiting and account recovery controls; consider MFA for sensitive operations. | Verify raw passwords are never persisted; test valid/invalid login, generic failure responses, account-state checks, and rate limiting. | **Partially implemented.** Registration stores BCrypt hashes (strength 12), enforces 12-character minimum and BCrypt's 72-byte limit, and authentication uses database-backed users with generic login failures. V6 stores USER/ADMIN roles; ADMIN is available only by an operator-controlled one-time bootstrap of an existing enabled account, not public registration. V2 schema was reported validated on PostgreSQL 18.6; Phase 5 roles/behavior were H2-tested only. Rate limiting, MFA, email verification, and recovery are not implemented. |
| Authorization bypass | A logged-in user reaches an operation or record outside their allowed role or ownership scope. | Exposure or alteration of another customer's financial data. | Define least-privilege roles; apply route and method authorization; check ownership in application services and queries. | Test unauthenticated and insufficient-role access, plus ownership checks on protected operations. | **Partially implemented and H2-tested.** `/account`, `/accounts/**`, and `/transactions/**` require `ROLE_USER`; `/admin/**` requires `ROLE_ADMIN`. Admin services also check the authenticated account's enabled state and persisted ADMIN role. Tests cover ordinary-user and anonymous admin-route denial and admin access. Account/transaction owner checks remain covered by Phase 3/4 integration tests; method-security annotations are not used. |
| IDOR / cross-user object access | A user changes an account, transaction, budget, or audit identifier in a URL or form and accesses another user's object. | Unauthorized disclosure or modification of financial records. | Resolve records through the authenticated user's scope; do not rely on unguessable IDs; reject unauthorized objects consistently. | Create two users and verify user A cannot read or modify user B's records by changing identifiers. | **Account and transaction history ownership implemented and H2-tested.** Cross-user account details/rename/close are denied; transaction history scopes by authenticated owner. Audit history is exposed only within the admin dashboard, protected by admin authorization. Budget routes do not exist. |
| Session theft or fixation | An attacker steals a session cookie or causes a victim to authenticate with a known session identifier. | An attacker can act as the victim until the session is invalidated. | Use HTTPS in deployment; set Secure, HttpOnly, and appropriate SameSite cookie attributes; rotate the session at authentication; set idle/absolute expiry; invalidate on logout. | Verify cookie attributes, session ID rotation at login, expiry behavior, and that logout invalidates the session. | **Partially implemented.** Session fixation migration and logout invalidation are configured. Session timeout is 15 minutes; HttpOnly and SameSite=Lax are configured. Secure cookies are on by default and off only in dev/test. Admin disable expires tracked sessions, but session invalidation has no dedicated integration assertion. Cookie attributes and fixation rotation also lack dedicated assertions. |
| Cross-site request forgery (CSRF) | A victim's browser sends an authenticated state-changing request initiated by another site. | Unauthorized profile changes or financial operations performed with the victim's session. | Keep CSRF protection enabled for session-based web forms; include tokens in state-changing forms; avoid state changes on GET. | Verify POST without a token and with an invalid token is rejected, while a valid-token request follows the normal authorization rules. | **Implemented for current forms.** CSRF remains enabled; Thymeleaf emits form tokens. Tests verify a token is rendered, a tokenless registration POST is rejected, and token-bearing login/registration/logout requests work. |
| Financial transaction integrity | A bug or malicious request posts unbalanced, cross-currency, duplicate-sided, partially committed, or later-modified entries. | Incorrect balances, unreconcilable books, or financial loss. | Post entries inside one database transaction; require debit/credit equality per currency; constrain entry shape; make posted entries immutable; correct them with reversals. | Test unbalanced and cross-currency posting rejection, rollback on partial failure, posted-entry mutation/deletion rejection, and reversal correctness. | **Migration/schema verified on PostgreSQL; operation workflows H2-tested.** PostgreSQL V1–V10 are successful, the V10 transaction-type constraint is validated, and both journal triggers are enabled; the V5 entry guard has the expected parent-row locks. H2 tests cover balanced posting, rollback, mutation rejection, and concurrency. The application has no reversal workflow; reversal correctness remains unimplemented and untested. |
| Idempotency replay or collision | A client retries a request after a timeout, or reuses a key with a different transfer payload. | Duplicate money movement or an incorrect prior result being returned for a different request. | Enforce a unique idempotency key in the database scoped to the authenticated owner; store a canonical request hash and resulting transaction; return the original result only for a matching retry. | Test repeated identical requests, same-key/different-payload rejection, and concurrent duplicate requests against PostgreSQL. | **Implemented and H2-tested.** Requests hash operation, account IDs, currency, and normalized amount; the existing `(owner_id, idempotency_key)` unique constraint and owner-row lock protect posting/replay. Identical retries return the original transaction; changed payloads using the key are rejected. PostgreSQL and concurrent same-key requests were not tested in this phase. |
| Concurrent transfers / double spend | Two simultaneous transfers each pass an insufficiently synchronized balance check against the same funds. | Account overspending or inconsistent account balances. | Lock affected account rows in a stable order inside the transaction; check available funds after acquiring locks; commit both transfer legs atomically; use retries only with idempotency protection. | Run concurrent PostgreSQL transfers against the same balance; verify no overspend, no one-sided transfer, and balanced ledger entries. | **Implemented and H2-tested.** Operations lock the owner row and then owned financial accounts in ascending ID order before checking balances; journal entries and idempotency records commit atomically. A concurrent two-withdrawal H2 test confirms only one can spend shared funds. PostgreSQL locking/concurrency was not verified in this phase. |
| Audit trail tampering or gaps | A privileged user or compromised application changes/deletes audit events, or a sensitive operation is never recorded. | Loss of accountability and inability to investigate or reconcile disputed activity. | Write audit events atomically with sensitive operations; make the audit store append-only to application roles; restrict access; record actor, action, target, time, and outcome without secrets. | Verify each sensitive action creates the expected event; verify ordinary application access cannot update/delete events; verify failed transactions do not leave misleading success events. | **Implemented and H2-tested.** Registration, account creation/closure, deposits, withdrawals, transfers, operator bootstrap, and admin enable/disable actions append metadata in the operation transaction. Audit update/delete attempts are rejected by H2 triggers and no application mutation endpoint exists. Admin-only dashboard lists events. PostgreSQL V7 trigger SQL and live PostgreSQL behavior remain unverified. Registration/bootstrap have no authenticated actor and are recorded with a null actor plus source metadata. |
| Credential/configuration disclosure | A committed or shared development configuration contains a reusable database credential, or diagnostic output exposes sensitive configuration. | Unauthorized database access and possible access to financial data. | Remove credential fallbacks from tracked files; inject secrets through local IDE environment settings or a secret manager; rotate any real credential exposed in source; keep diagnostic logging appropriately scoped. | Scan tracked files and logs for credential values; verify startup fails when required credentials are absent outside tests. | **Partially mitigated.** The hard-coded development password fallback was removed and the password remains environment-sourced. The reported PostgreSQL 18.6 connection confirms configured credentials could authenticate, but does not verify secret storage or log redaction. Custom `UserDetailsService` prevents Spring Security's generated in-memory credential from being used; the final test startup did not log a generated password. Rotate the prior credential if it was real or shared; secret scanning and production secret-manager setup remain outstanding. |
